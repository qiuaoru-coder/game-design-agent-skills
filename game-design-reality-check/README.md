# 游戏策划现实校验器

> 别用感觉证明好玩，用目标、机制和证据验证设计。

## 大白话介绍

做游戏最危险的一句话往往是：“我觉得这个肯定很好玩。”

问题不是策划不能有直觉，而是我们很容易把自己的想象、对规则的熟悉、已经投入的工作量，误当成玩家真的会喜欢。这个 Skill 就像一个不会为了照顾情绪而点头的策划搭档：它会把你的方案拆开，告诉你哪些已经有依据，哪些只是逻辑上说得通，哪些仍然是未经验证的假设，以及哪个地方最可能先翻车。

它不会隔着文档替你宣布游戏好玩，也不会为了显得专业而把所有方案都批判一遍。它真正做的是：把“玩家会觉得刺激”“这个系统很有深度”“这个玩法能长期留住人”之类的大话，改写成能够制作、观察和验证的假设，再给出最低成本的原型或试玩方案。

## 它适合做什么？

- 检查一个游戏点子是否只是听起来很美
- 审查玩法、系统、关卡、功能或完整策划案
- 找出“目标很好，但机制根本支撑不了”的地方
- 区分事实、推导、假设和未知信息
- 检查选择是否真的有深度，还是只有一个标准答案
- 判断情绪、沉浸、创新、留存等结论有没有证据
- 在继续投入制作前，找出最应该先验证的问题
- 根据试玩记录或数据，重新判断原来的策划假设

## 最简单的用法

```text
使用 $game-design-reality-check：

这是我的玩法想法：玩家在黑暗森林里只能依靠声音判断怪物的位置。
请不要顺着我夸，帮我检查它是否真的可能产生紧张感，
指出最大的幻想成分，并设计一个最低成本的验证原型。
```

也可以直接粘贴策划案：

```text
使用 $game-design-reality-check 审查下面这份系统方案。
请区分已经成立的设计逻辑和未经验证的好玩假设，
并按“现在修改、先做原型、验证后再做”给出行动顺序。

[粘贴策划案]
```

## 最好给它什么信息？

只有一句灵感也能开始。想得到更准确的结果，最好提供：

```text
游戏或功能是什么：
目标玩家是谁：
玩家要反复做什么、决定什么：
希望玩家产生什么体验：
你为什么认为它会好玩：
目前已有的原型、试玩、数据或参考游戏：
团队、时间、平台和制作限制：
你现在要决定什么：
```

其中最有价值的一项是：**你为什么认为它会好玩？** 这句话通常能直接暴露最需要验证的假设。

## 它会给你什么结果？

根据你的问题，它可以输出：

- 一句话现实判断：当前是没有检查、逻辑可行但未验证、可以测试、已有初步证据，还是已经被证据反驳
- 核心承诺：这个设计究竟希望什么玩家因为什么机制产生什么行为和体验
- 证据账本：哪些是观察事实、外部依据、规则推导、主观假设或未知
- 最弱环节：最可能让整个方案失效的那条因果链
- 反方推演：玩家可能怎样绕开、误解或优化掉设计者想要的体验
- 修改优先级：现在该删什么、改什么、暂时不要做什么
- 验证方案：最小原型、试玩对象、观察行为、成功／修改／停止信号

## 怎么理解它的判断？

它不会简单打出“好玩”或“不好玩”，而会使用更诚实的结论：

- **没有检查**：连需要验证的核心说法都不清楚
- **逻辑可行但未验证**：策划逻辑讲得通，还没有玩家证据
- **可以测试**：假设、原型和判断标准已经明确
- **已有初步支持**：相关证据在一定范围内支持方案
- **受到反驳**：规则或实际观察与原来的说法冲突

这样的判断不会替你做创意决定，但能防止团队在最关键的问题尚未回答时，就开始大量制作内容。

## 最后提醒

Skill 可以帮你更早发现逻辑漏洞和证据缺口，但不能代替真人试玩、数值验证、竞品与市场研究，也不能仅凭文字预测最终游戏品质。它的价值不是替你下结论，而是让你知道下一笔时间和制作成本应该花在哪里。
